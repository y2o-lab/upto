03

チャンクの進捗はCloudflareに残す

分割の計算はVercel、次に実行するチャンクの選択と完了記録はCloudflareです。各段階を選ぶと詳細を表示します。

二重起動と二重保存を防ぐ

Cloudflareが実行枠と安定したWorkflow IDを管理。Vercelはstageごとのoperation IDで保存済み結果を確認し、同じ処理への再配送を安全に扱います。

チャンク2で失敗

D1：chunk1 完了→chunk2 再試行→chunk3 未実行

Cloudflareが再試行時刻を管理し、Vercelにchunk2を再依頼。本文と生成結果はPostgreSQLに保存し、大きいpayloadをCloudflareへ返しません。

保存成功後にHTTP応答を失う

Vercel：結果を保存→応答を失う→同じoperation IDで照会

再実行では保存済みresult IDを返し、Cloudflareが進捗を確定。D1とPostgreSQLの間に分散transactionはないため、定期照合でも回復します。

Cloudflare↔Vercelは双方向で認証。期限・nonce・環境を検証します。LLM応答そのものを失った場合の二重課金を完全に防げるとは限りません。

Cloudflare料金 $0 を優先

有料Containersは使いません。CloudflareとVercel両方の無料枠を実測し、余裕を持った記事数と並列数に設定します。GeminiとDBの料金は別です。

Vercelの利用条件と実行上限

Hobbyは非商用の個人利用向け。起動はCloudflareなのでVercel Cronの頻度制限は使いませんが、各Functionの5分制限と月間usage制限は残ります。

次の一歩：小さいHTTP制御＋1記事で検証。
Vercelでjsdom/SDKが動くこと、CFの制御が10msに収まること、期限切れ・応答喪失・429から回復すること、Terraform再applyで不要な差分がないことを確認します。
06

両サービスのインフラをTerraformで管理

Cloudflareリソース

  • Worker / bindings / observability
  • Cron / Workflow定義
  • Queue / DLQ / consumer / retry設定
  • Durable Object SQLite class・migrations
  • D1 database / DNS

Vercelリソース

  • collector専用project / Git連携
  • Node.js・build設定 / domain
  • 環境別の非secret設定
  • 既存Webとdomainを保持
  • アプリのコードはCIでdeploy
fmt / validate→planをレビュー→apply→migration / secrets / deploy→疎通確認後にCron有効化

既存infraとR2 stateを拡張

batch用moduleとstate keyを追加し、staging/productionを分離。既存Webと外部管理のstate bucketを再作成しません。固定provider versionのschemaとbootstrapをPoCで検証。

状態データとsecret値は別に管理

業務データ・Workflow instanceはruntime、schema migrationはCI。runtime secret値は各secret storeへ注入し、Terraform stateに入れません。同じリソースをWranglerと二重管理しません。
