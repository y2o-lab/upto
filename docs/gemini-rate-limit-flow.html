03

数える単位は「記事」ではなく「APIリクエスト」

並列に到着するリクエスト
記事A / チャンク1記事A / チャンク2記事A / 最終統合記事B / 通常要約重要→通常 / fallback429後 / 再試行
→
Google project単位のDOモデル別の枠＋全体の保守的な枠
staging / productionも同じprojectなら共有

RPM：送信回数 / 分

各attemptを数える。記事が4つのAPI呼び出しを使うなら4回分。単なる同時実行数の制限では守れません。

TPM：入力token / 分

本文とpromptを含む入力tokenを見積もり、安全余裕を持って予約。長い入力は、回数が少なくても上限に達します。

RPD：送信回数 / 日

日次枠を使い切ったら保留。Google側の日次リセットは太平洋時間0時。夏時間も考慮します。

API keyを増やしても、同じGoogle projectの枠は増えません。
実クォータはモデルと利用tierに依存します。同じprojectを使う別アプリがgateを通らない場合、その消費はローカルに把握できません。全利用をgateへ集約するか、余裕を残して監視します。

05

429が返っても、そのまま再送しない

Gemini → 429Vercelがエラーを分類
↓
待機情報とattemptを記録Retry-After / 公開されるretry情報を優先
なければ上限付きbackoff＋jitter
↓
CF Workflowでsleep対象クォータの共有cooldownも更新
他の実行が即座に送り続けない
↓
Vercelを再依頼 → 新しいgate判定同じoperation ID / 新しい認証nonce・permit

短い制限・一時的な429

待機して限定回数だけretry。初期案は追加2回。枠不足でGeminiを呼ばなかった待機は、API attemptとは別に管理します。

日次枠・入力が大きすぎる

日次枠ならリセットまで保留。1入力だけでTPM枠を超えるなら分割・縮小が必要です。短いsleepを繰り返しても解決しません。

上限を超えるretry、認証・設定エラー、回復不能な出力は失敗として記録して通知。他の記事は継続します。SDK、Workflow、Queueで同じAPI retryを重ねません。

06

「制御できる」と判断するための実装・検証

共有ゲートへ追加する状態

  • project ID / model / RPM・TPM・RPDの設定
  • 直近のpermitとtoken予約 / 日次カウント
  • cooldownの終了時刻 / permitの有効期限
  • 同じattemptの重複許可を防ぐID
  • SQLiteへの永続化と再起動後の復旧

必須の検証

  • 複数Vercel invocationでも合算上限を守る
  • チャンク・統合・fallback・retryが全てgateを通る
  • TPM不足・RPD終了・429で正しく保留する
  • permit失効・時計差・通信遅延・再起動
  • SDK内部retryとgate外の利用を検出する
現在は「回数制御が一部実装済み」。移行後の分散制御はこれから実装する設計です。
実クォータをAI Studioで確認し、入力token見積もりと共有状態の動作を検証します。Google側の実際の容量は変動するため、予防的な制御に加えて429の回復経路を持ちます。
